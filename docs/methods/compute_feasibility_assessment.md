### 2.1 三种规模场景

| 场景 | 原始数据需求 | 含中间产物峰值 | 本机可行性 |
| --- | --- | --- | --- |
| **S：原论文同等规模**（~300 份 @5× 建库 + 100 份测试） | FASTQ ~190 GB | +BAM ~300 GB ≈ **490 GB** | ❌ 超出 424 GB（除非边算边删） |

### 2.2 计算时间估算（按 32 线程、BWA-MEM2 约 5–10 Gb 序列/小时）

| 步骤 | 单样本 | 180 份合计 | 说明 |
| --- | --- | --- | --- |
| BWA-MEM2 比对（5×） | 12–25 min | **40–75 小时**（2–4 天连续） | 可 32 线程并行；瓶颈在 CPU，不在磁盘 |
| bcftools mpileup+call | 20–40 min | 60–120 核心·小时 → 并行后 4–10 小时 | 不要用 GATK HaplotypeCaller（慢 3–5 倍） |
| mosdepth read-depth（CNV 路线） | 5–10 min | ~20 小时 | 轻量 |
| KMC / Jellyfish（k=21–51） | 5–15 min | ~30 小时 | 内存敏感，用 `-m` 限流 |
| SNP 矩阵构建 / PCA / 距离 | — | 数小时 | 占内存，需分块 |
| ulcWGS 下采样模拟（7 档 ×10 重复） | < 1 min/档 | **数小时** | 关键：**从同一 BAM 抽 reads，不要每档重新比对** |
| 标记召回 / 相似度 / 鉴定准确率 | — | 数小时 | 纯矩阵运算 |

**合计量级：约 1–2 周的不间断计算**（不是"跑一晚就完"），且必须容忍"跑 3 天出结果"。这对一台笔记本是合理的，对 1000 份规模则要乘以 5 倍以上。

## 三、三个硬约束（按严重程度排序）

### 约束 1：内存 16 GB（最致命）

- WSL2 默认只拿到 ~8 GB，而**水稻 BWA-MEM2 索引加载就需约 5–6 GB**（索引文件本身 4–5 GB），几乎没给 samtools sort 和页缓存留空间 → 必然 OOM 或疯狂换页。
- 后续"大矩阵"步骤（数千样本 × 百万位点、PCA、pairwise 距离）会进一步吃内存。
- 缓解：写 `.wslconfig` 把 WSL 提到 12–13 GB（Windows 侧只剩 ~3 GB，日常会卡）；`samtools sort -m 1G`；KMC `-m 4`；矩阵分块落盘。

### 约束 2：磁盘 424 GB 可用，且 C:/D: 是同一块物理盘

- 不能用"C 盘放系统、D 盘放数据"来规避总量限制——总池子就是 424 GB。
- WSL 的 ext4 虚拟盘在 **C:**（当前 9 GB），写进 WSL 内部会持续吃 C: 那 174 GB；而把数据放 `/mnt/d` 不占 C:，但 drvfs 跨文件系统 I/O 比 ext4 慢（大量小文件时尤其明显）。
- 建议：**FASTQ/BAM 放 `/mnt/d`（不占 C:），比对与排序的临时文件放 WSL ext4（快）**，并在 `.wslconfig` 里给 WSL 留够 C: 空间。

### 约束 3：网络下载时间可能超过计算时间

- 190 GB FASTQ 在 2 MB/s 下要 **26 小时**，在 1 MB/s 下要 **53 小时**。
- 缓解：`fasterq-dump`/`prefetch` 用 ENA 的 FTP（通常比 SRA 快）、多线程并行下载、断点续传、边下边算。

## 四、结论

| 阶段 | 本机可行性 | 备注 |
| --- | --- | --- |
| Phase 0–2（初始化 / 论文解析 / 路线设计） | ✅ 完全没问题 | 已完成 |
| Phase 3–4（公共数据检索 / 样本表） | ✅ 没问题 | sra-tools / entrez-direct 已就位 |
| Phase 5（Pilot 20–50 份） | ✅ 轻松 | 50 份 @5× 仅约 31 GB |
| Phase 6–7（QC / 参考基因组） | ✅ 没问题 | 参考基因组仅约 400 MB |
| Phase 8–11（SNP / k-mer / CNV / SV 四条路线，~180 份） | ⚠️ **可行，但要 2–4 天不间断计算 + 严格管理磁盘** | 内存必须调优 |
| Phase 12（标记综合比较） | ✅ 没问题 | 纯计算 |
| Phase 13（ulcWGS 模拟 7 档 × 10 重复） | ✅ 没问题（前提：从同一 BAM 下采样，不重新比对） | 这是本项目的核心，恰好很轻 |
| 数据库 / Web 系统 | ✅ 没问题 | 可选后续补充 |
| **1000+ 份的原始 FASTQ 全流程** | ❌ **不可行** | 磁盘差 3 倍、内存不足；改用公开 VCF 矩阵即可绕过 |

**一句话结论：这台电脑能做出一篇水稻品种数字身份证的方法学论文，但必须把"原始高深度 FASTQ"控制在 200 份左右，参考库指纹用公开 VCF 矩阵构建；1000 份以上的原始测序数据在这台机器上不可行。**

### 一个重要的规模安慰

参考论文用的是**小麦**：16 Gb 六倍体基因组、528 份材料、平均 5.4× ≈ **15 TB FASTQ**——这台机器连零头都装不下。
水稻基因组只有小麦的 **约 1/40**，同样设计只要 **约 380 GB**。**"这台机器做水稻勉强可行、做小麦完全不可能"**，这也从算力角度反证了选择水稻作为第一物种是对的。

### 另外：项目的创新点不依赖样本量

对照 Niu et al.（528 份建库 + 1071 份公共数据），本项目论文的增量在于：
1. **7 档深度 × ≥5–10 重复**的精细深度—召回曲线（原文只有 6 档、2 批重复）；
2. **水稻专属阈值重算**（ROC/AUC/F1，原文没有 ROC/AUC）；
3. **四条标记路线横向实测比较**（原文只做 CNVb）。

这三条都**不需要 1000 份原始数据**——200 份足够支撑，且计算量恰好落在这台机器的能力范围内。

## 五、改进建议（按性价比排序）

| 优先级 | 措施 | 约成本 | 收益 |
| --- | --- | --- | --- |
| ★★★ | **内存 16 → 32 GB**（加一条同规格 DDR5-5600 SO-DIMM；当前是单条，另一插槽大概率空闲） | ¥300–700 | 一次性解除 WSL 内存上限、samtools sort、联合分型、大矩阵四个瓶颈；**性价比最高** |
| ★★☆ | **加 2 TB NVMe SSD** | ¥700–1200 | 解锁 500–1000 份原始数据规模 |
| ★☆☆ | 4 TB 移动硬盘做冷存 | ¥500–700 | 只能存档；比对时读速慢，不解决计算瓶颈 |
| ★★★ | **用学校服务器/集群做"下载 + 比对"**，本机只做分析与写作 | 0 | 最省钱；本地网络吞吐和长任务稳定性都不如集群 |
| ★★☆ | 软优化（免费）：`.wslconfig` 调内存与 swap、数据放 `/mnt/d`、临时文件放 ext4、CRAM 替代 BAM、边下边算、长任务过夜跑 | 0 | 可把可用规模提升约 50% |

### `.wslconfig`（✅ 已于 2026-09-16 创建于 `C:\Users\86159\.wslconfig`，并实测生效）

```ini
[wsl2]
memory=10GB            # 实测 free -h 显示 9.7Gi
processors=16          # 实测 nproc = 16
swap=16GB              # 实测 free -h 显示 16Gi
swapFile=D:\\wsl-swap.vhdx
[experimental]
autoMemoryReclaim=gradual    # 空闲时把内存还给 Windows
sparseVhd=true               # ext4.vhdx 删除文件后自动收缩，防止悄悄吃满 C 盘
```

> - `swapFile` 放到 D: 可避免 swap 占用 C: 空间；
> - `memory` 由原计划的 12 GB **下调为 10 GB**：物理内存仅 15.7 GB，留 5.7 GB 给 Windows 更稳妥。
>   实测表明本项目在 10 GB 下足以跑通全链路基准（各步骤峰值内存最高 2.0 GB）；
> - `sparseVhd=true` 解决"WSL 虚拟磁盘只涨不缩"的老问题，对 C: 盘紧张的本机尤为重要。

## 六、本机算力实测：✅ 已完成（2026-09-16）

> 本节原为"待办"。**现已执行完毕，本文档前述的估算吞吐应以下方实测值替换。**

最终采用的基准脚本是 **`scripts/bench2.sh`**（而非初版 `scripts/bench.sh`）。原因：
`bench.sh` 规模过小（20 Mb 合成参考、30 Mb 序列），测得的 "54 Gb/h" 几乎全是进程启动开销，
`samtools sort` 甚至 <1 秒而触发除零崩溃——**小规模基准会给出虚假的高吞吐**，这一点在 TASK-052 中必须避免。

`bench2.sh` 改用**真实 IRGSP-1.0 参考序列**的 1 号染色体（43.27 Mb）@ 10×，按实际基因组 375 Mb 外推（×8.666）：

| 步骤 | 实测核时/样本 | 占比 |
| --- | ---: | ---: |
| **bwa-mem2 比对** | **0.565** | **69.8%** |
| bcftools 变异检测 | 0.127 | 15.8% |
| KMC k=31 | 0.039 | 4.8% |
| samtools sort | 0.035 | 4.3% |
| 读段模拟（numpy） | 0.021 | 2.6% |
| → CRAM | 0.014 | 1.8% |
| mosdepth | 0.006 | 0.8% |
| **合计** | **0.809** | 100% |

→ **单样本 10× 全基因组：墙钟 12.1 分钟，CPU 0.81 核时**

**两处重要更正**：

1. 本文档前述「每样本 **10–31** 核时」**高估 4–12 倍**——
   该数字来自人类/植物尺度文献外推，未按水稻 375 Mb（约人类的 1/8）正确折算；
2. 「bcftools 变异检测是最大单项瓶颈」**不成立**——实测 **bwa-mem2 比对占 69.8%**，
   变异检测仅 15.8%。**优化重心应放在比对环节**（或评估改用 minimap2）。
