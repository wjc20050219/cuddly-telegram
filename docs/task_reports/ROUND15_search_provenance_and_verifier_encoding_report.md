## 3. 发现一：权威汇总文件里根本没有这个查询

`data/metadata/search/ena_search_summary.tsv` 只有 7 行，查询标签为
`OS-WGS`、`OS-WGS-GENOMIC`、`OS-any-strategy`、`OS-cultivar-in-title`、
`Oryza-genus-WGS`、`DRA-submitted-WGS`、`OS-WGS-paired`——

**没有任何一条带深度阈值**。也就是说 `≥10×` 这个口径不在权威汇总里。

进一步全局搜索 `24633` / `24,633`：只命中两处——

- `data/metadata/search/README.md` 的"关键数字速查"表；
- `scripts/task011_fetch_ena.py` 的模块 docstring 注释。

而 `scripts/search_round2.sh` 第 66–69 行**确实**用 `limit=0` 计数查询打印过
`>=1x`、`>=5x`、`>=10x`、`>=20x` 四个数字。**它们只被打印到控制台，从未落盘。**

## 4. 发现二：清单文件是截断的

顺手数了一下两个清单文件的行数：

| 文件 | 数据行数 | 脚本中的 `limit=` |
| --- | ---: | --- |
| `ena_rice_wgs_runs.tsv` | 5,000 | `search_ena.sh` 用 `limit=5000` |
| `ena_rice_wgs_deep_runs.tsv` | 10,000 | `search_round2.sh` 用 `limit=10000` |

**两个数字都恰好等于页上限。** 这是截断的特征，不是自然总数。

两个脚本的行为模式完全相同：**先**用 `limit=0` 得到精确总数，**然后**用有限的
`limit` 下载，**但从不比较两者**。于是截断被静默保留，
`analyze_deep.sh` 又在新清单上做平台/深度/来源分布统计——
这些统计的口径因此是"前 10,000 条"，而不是"全部 ≥5× 记录"。

## 5. 修复：让问题可见且可机检

本机没有下载授权，**不能**重新拉取数据。所以修复的目标不是"补齐数据"，
而是**让这个已知缺陷无法再被忽略**：

| 措施 | 文件 |
| --- | --- |
| 生成来源与完整性记录，截断项显式标注 `suspected_truncated` | `scripts/record_search_provenance.py` → `search_provenance.json` |
| 两个下载脚本在行数等于 `limit` 时**打印截断警告** | `search_ena.sh`、`search_round2.sh` |
| 撤下无法复核的三个深度分档数字 | `search/README.md`、`server_admin_questions.md`、`task011_fetch_ena.py` |
| 改用有存档来源的数字（96,623，出自 `ena_search_summary.tsv`） | 同上 |
| 锁定"计数 ≠ 清单"这一区分 | `tests/test_search_provenance.py`（15 项） |

### 5.1 影响范围的界定

这是本轮最重要的判断。发现截断后，必须回答：
**两个已冻结的面板是否因此失效？**

测试逐项断言了三点，答案是**不受影响**：

1. 面板样本取自 `data/metadata/candidates/candidate_samples.tsv`，
   该表远大于被截断的清单（>10,000 行）；
2. 每个面板都**存在**不在被截断清单中的样本（pilot 30 中有 21 个不在，
   independent 25 中有 18 个不在）——若全部来自该清单，截断才是致命的；
3. 面板中每个 run 都能在候选表中找到。

受影响的只是**发现阶段与筛选阶段的统计口径**，而非入选样本本身。

> 若不做这一步界定，读者无法判断这个缺陷是否推翻了此前的工作。
> "说清楚它不影响什么"和"说清楚它影响什么"同样重要。

## 6. 发现三：校验脚本在真实数据上崩溃

按顺序运行全部 6 个校验脚本时，`verify_pub_match.py` **以非零码退出**。

排查后确认：**不是它查出了问题，而是它自己死了。**

```
UnicodeEncodeError: 'gbk' codec can't encode character '\xa0' in position 14
```

它从 Europe PMC 取论文摘要并打印，而**第一个案例的摘要里就有一个
非断行空格（U+00A0）**，本机控制台是 GBK 代码页。

这类缺陷对**校验工具**尤其危险：工具崩溃看起来像"没查出错"，
而它本该是"唯一能发现错误的东西"。一个只在干净输入上能跑的工具等于没有工具。

### 6.1 修复过程中的第二次错误

第一版修复用 `sys.stdout.encoding` 取编码。看起来对，**但在测试里立刻漏了**：

在 `redirect_stdout` 之下，`sys.stdout` 是一个**没有 `encoding` 属性**的
`StringIO`，`getattr(..., None)` 回退到 `"utf-8"`，于是 `\xa0` 照样漏过去。

暴露它的是我写的一项测试——它断言"重定向后 `\xa0` 必须已被替换"，
结果 `\xa0` 原样返回。改为在**导入时一次性捕获**真实控制台编码后通过。

修复后 `verify_pub_match.py` 退出码 0，并**真正完成了它的使命**：
确认案例 B（PRJNA743713 → PMID 34564276）是一篇**稻飞虱抗性**论文，
与"Fuzhou 水稻样本"项目并非同一研究——即全文匹配确实存在错配。

## 8. 一次自己造成的损坏（诚实记录）

在更新附录 D 的计数时，我用 PowerShell 的
`(Get-Content -Raw) -replace ... | Set-Content -Encoding utf8` 做了原地改写，
**结果把文件写坏了**：`Set-Content -Encoding utf8` 加了 BOM，
且 `-replace` 往返损坏了中文（乱码）并压掉了部分换行。

这**正是我自己在 LRN 中写下的禁令**："永远不要用 PowerShell 改写仓库文本文件"。
违反禁令的代价是：没有 git、没有备份，只能凭对话中的完整内容重写该文件。
重写后已通过全部检查，并**新增一项测试**断言该文件不含 U+FFFD 且关键术语完好。

> 教训：把禁令写下来不等于会遵守。**唯一的可靠防线是让工具在结构上不可用**
> （例如仓库初始化 git），而不是靠记性。
