## 二、真实缺陷 1：文档声称的缺陷早已不存在

**可疑陈述**（`docs/methods/reference_genome_plan.md:65`）：
> 必须把完整 SHA256 写入记录，不能只保存前 16 位。
> 当前 `server/03_align.sh` 的历史实现只截取前 16 位，需在服务器试跑前修正并验证。

**验证**：直接读脚本。

| 检查 | 实际 |
| --- | --- |
| `03_align.sh:45-47` 取摘要的方式 | `sha256sum "$gz" \| awk '{print $1}'` —— **完整 64 位** |
| 是否存在 `cut -c1-16` / `head -c16` 之类截断 | **不存在** |
| `reference_record.tsv` 列数 | 9 列，含 `gzip_sha256` 与 `fasta_sha256` 两个独立摘要 |

**结论：代码是对的，文档是错的。** 这是一条早就修好、但文档没跟上的陈述。

**修复方式不只是改文字**，而是把它变成机械不变量——
`verify_undergraduate_scope.py` 新增 3 项检查：

1. `03_align.sh` 中不得出现任何截断模式（`cut -c1-16`、`head -c16`、`[0:16]` …）；
2. 记录必须同时含 `gzip_sha256` 与 `fasta_sha256`；
3. 必须至少两处 `sha256sum`（压缩文件与解压 FASTA 各自独立校验）。

**证明这个不变量有牙齿**（不然它只是一个永远通过的检查）：
把 `cut -c1-16` 注入真实的 `03_align.sh`，检查器**退出码 1** 并报出
`found: ['cut -c1-16']`；随后文件按字节还原。该过程已固化为
`tests/test_checksum_invariant.py`（3 项，含"还原后必须重新变干净"）。

## 三、真实缺陷 2：失败退出码的报法依赖排版巧合（已加固）

`server/run_all.sh:115` 原文：

```bash
else
  log "阶段 $st 失败（退出码 $?），流水线中止。…"
```

**可疑陈述（我的假设）**：`log` 调用会把 `$?` 冲掉，于是报出的不是脚本的退出码。

**实测/推演结论：假设不成立，代码是对的。** 依据两条规则：

1. `then` / `else` **不是命令**，进入 `else` 分支时 `$?` 仍是被测命令的状态；
2. 参数中的 `$?` 在 `log`（及其内部的 `$(date …)`）**执行之前**就已经展开完毕。

因此当前写法恰好报出正确退出码。

**但它"只是碰巧对"**：只要有人在 `log` 之前插入任何一行真实命令，
这里报出的数字就会**静默**变成那条命令的状态——
而这条日志正是服务器上排错时唯一能看到的线索。
（全仓 `server/*.sh` 中 `$?` **只此一处**，影响面就是这一行。）

**加固**：先 `rc=$?` 再使用。附 5 项静态测试
（`tests/test_run_all_resume.py`），其中一条是反向断言：
**不允许再出现 `log` 里直接展开 `$?` 的写法**。

同样做了变异验证：在 `else` 与 `rc=$?` 之间插入一行 `:`，
`test_the_capture_immediately_follows_the_else` **如预期失败**；
真实文件未被改动。

> **我自己的测试又写错了一次**：最初断言 `rc=$?` 必须紧邻 `else`，
> 但我在两者之间加了 4 行**注释**——注释不改变 `$?`，是断言太死板。
> 已改为"向上跳过注释与空行后撞上 `else`"。本轮 6 个新断言里，
> 错的是我的期望，不是代码。
