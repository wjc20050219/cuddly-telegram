## 2 为什么写这个工具

`server/00_probe.sh` 会输出一张 `probe_summary.tsv`，里面是 30 个键值：
CPU 核数、内存、**家目录剩余空间**、**调度器**、7 个软件管理器、
18 个工具的可用性、**ENA/NCBI 下载速度**。

这些数字决定了后面**每一步怎么做**：能不能在服务器上下载、
要不要分批、并行几个、用不用 Slurm、缺的工具装不装得上。

此前这些判断只写在 `docs/server_admin_questions.md` 的散文里，
**没有任何东西检查它与 `00_probe.sh` 的实际输出是否对得上**。
本轮把它写成 `scripts/interpret_probe.py`，
于是它对不对，可以由测试回答。

**它现在还没跑过真实探测数据**——`probe_summary.tsv` 不存在。
本轮的"场景"全部是**构造的输入**，只用于检验规则，
**不是测量结果，不得当作本项目的发现引用**。

## 3 通过跑场景发现的第一个真实缺陷

我先把规则写出来，再构造 12 个场景去**证伪**它。当场抓到两个真缺陷：

### 3.1 `use_slurm` 与 `run_all.sh` 的实际能力不符（严重）

我原本写：

```python
d["use_slurm"] = sched in ("sbatch", "qsub", "bsub")   # 错
```

语义是"这台机器装了什么调度器"。但 `run_all.sh` 第 41 行是：

```bash
HAVE_SLURM=0
command -v sbatch >/dev/null 2>&1 && HAVE_SLURM=1
```

**只认 `sbatch`，没有 PBS/LSF 分支。**
于是在一台有 `qsub` 的机器上，我的工具会说"就绪，Slurm 会接管"，
而实际上流水线会**在登录节点上跑全部比对**——
这正是管理员最可能直接杀进程的场景。

改为 `d["use_slurm"] = sched == "sbatch"`，并新增一个字段
`scheduler_usable_by_run_all` 把"机器有什么"与"脚本能用什么"分开。
测试现在**直接读 `run_all.sh`**，要求存在 `command -v sbatch`
且**不存在** `command -v qsub` / `command -v bsub`，两份文件无法再各自漂移。

### 3.2 "空间未知"与"空间不足"共用一个动作提示

原本两者都输出 `存储受限：按上面的分批方案执行`。
但空间未知时**根本没有"上面的方案"**——那句话是空的。
现在分开：未知 → `磁盘空间未知：请提供 df -h 结果后再定分批方案`。

**教训**：只要补救措施不同，"未知"就必须与"不足"分开报。
未知需要的是一个**问题**，不足需要的是一份**方案**。

## 4 变异测试：第一次主动把代码改坏

写完 42 项测试后，我做了一件此前十五轮都没做过的事：
**把代码改坏，看测试是否真的会失败**。

结果分成两类，**处理方式完全相反**：

### 4.1 真实的测试漏洞（2 处，已补）

| 变异 | 当时结果 | 处理 |
| --- | --- | --- |
| 存储阈值改成恒不可达分支 | ❌ 全绿 | 补 100G/250G/300G/330G/400G 五档边界断言 |
| `REQUIRED` 工具集清空 | ❌ 全绿 | 补集合非空 + 必须含 samtools/bcftools/bwa-mem2/fastp |

这两个是**真的洞**：把存储分支写死、或把必需工具集合清空，
**整个套件依然全绿**——也就是说这两个功能此前**没有任何测试真正守着**。

### 4.2 语义等价的变异（3 处，"没抓住"是正常的）

| 变异 | 为什么没被抓住 |
| --- | --- |
| `REQUIRED = {} or {` | **字典没被清空**——`{}` 为假，`or` 返回右边 |
| 把已被前分支覆盖的 `elif` 改成 `False` | 该分支本就不可达 |
| 只改动作字符串的**前缀** | 测试本就只断言关键要素 |

**这是我这轮最重要的一个认识**：
"变异没被抓住"**不等于**"测试有漏洞"。
前两次我看到"NOT CAUGHT"就想再去改测试，
差点去改**本来正确**的测试。

### 4.3 最值钱的发现：一个名字响亮却毫无作用的测试

```python
def test_missing_tool_without_conda_is_a_hard_blocker(self):
    d = self.m.decide(make(tool_samtools="no", tool_bcftools="no", soft_conda="no"))
    self.assertTrue(d["blocking"])      # 通过
```

删掉"缺工具就阻塞"的规定后，**这个测试照样通过**——
因为输入里的 `soft_conda="no"` 已经通过**环境规则**把 `blocking` 置真了。
它测的是另一条规则，**从来没测过它名字里说的那条**。

> **一个测试只有在"被测规则是唯一能决定结果的因素"时才是守卫，
> 否则它只是装饰。**

已重写为两组用例：conda 存在时缺工具**不阻塞但必须被报告**；
conda 不存在时才是硬阻塞。并在 docstring 里写明这段经过。

## 5 我自己的错误期望（本轮 4 处）

跨轮累计，我的错误期望已明显多于真实代码缺陷。本轮：

1. 断言 `00_probe.sh` 里出现字面量 `tool_samtools`——
   实际是**循环生成** `kv tool_$t`，字面量根本不存在；
2. 断言 `probe_get ENA`——实际是小写 `ena` / `ncbi`；
3. 误以为"存储未知"分支写错了，**实为测试断言写错**；
4. 误以为 `qsub` 的 `use_slurm` 判断只是断言问题，
   实际**代码确实错了**（这是本轮唯一"测试对了、代码错了"的一次）。

第 1、2 条暴露一个通用问题：
**我在断言"文件里有某个字符串"，而文件是用循环/变量生成那个字符串的。**
测试必须解析**生成方式**（这里是 `for t in ...` 的词表），
而不是指望字面量出现。
